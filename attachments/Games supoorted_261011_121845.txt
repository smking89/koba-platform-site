Universal Modded-Server Framework for KOBA

The framework is now generalized so any multiplayer game that supports server-side modding (plugins, script extenders, Harmony patches, UE4SS, BepInEx, etc.) can be onboarded through a single, reusable pattern. Specific titles (ARK, Rust, Minecraft, CS2, Valheim, SCUM, Unturned, etc.) become concrete instances of this pattern rather than one-off integrations.

Universal extraction method

1. Install the game’s standard modding framework (or the lightest possible injector that can run code inside the dedicated server process).
2. Deploy a thin KOBA Connector plugin / mod written for that framework.
3. The connector registers for the framework’s standard event surface: 
◦ Player connect / disconnect / spawn
◦ Death / damage / kill
◦ Inventory / economy / currency changes
◦ Chat / commands
◦ Custom game events (tames, raids, objectives, etc.)
4. On each event the connector: 
◦ Extracts the platform identity (SteamID64, EOS ID, UUID, XUID, …)
◦ Builds a canonical KOBA event
◦ Signs and asynchronously POSTs it to the KOBA ingest endpoint

This pattern works for any game that already has a working server-side modding community. New games are onboarded by writing one small adapter plugin against the existing framework rather than inventing a new telemetry pipeline.

Efficiency ranking inside this archetype
• Highest: Native framework event hooks (zero polling, full object access).
• High: Harmony / UE4SS / BepInEx hooks that can reach the same events.
• Acceptable fallback: Periodic polling of player lists + differential detection when the framework lacks rich events.

B–D. Other Archetypes (Unchanged but Secondary)

• Native REST/Web endpoints (Palworld-style)
• Log-tailing + database listeners
• Competitive match APIs (CS2 Faceit, Valorant Tracker, etc.)

When a game supports modding, the Modded path is always preferred over pure log or external API approaches.

2. Cross-Network Player Identity Extraction (Unchanged Core + Universal Rule)

The identity resolution layer stays the same. The only addition is a framework-agnostic contract:

Every KOBA connector plugin must expose a single function:

GetCanonicalPlayerId(playerObject) → { platform: string, id: string }


The connector implementation for each game/framework fills this in with the correct field (SteamID64, EOS Product User ID, Minecraft UUID, etc.). The rest of the pipeline never cares which game produced the ID.

───

3. Bidirectional Automation Protocols (Generalized)

For any moddable game the preferred write path is:

1. Custom framework command / API call exposed by the KOBA connector itself
 (e.g. KOBA.GiveItem, KOBA.Broadcast, KOBA.WhitelistAdd).
 This is the most reliable and richest method.

2. RCON / native admin console (when the game or framework already supports it).

3. HTTP endpoint registered by the connector (many modern frameworks allow plugins to spin up a local HTTP listener).

Order of preference is always: Connector-native API → Framework command → RCON → external match API.

───

4. Dynamic Data Normalization Strategy (Unchanged)

The 4-part routing key and canonical event schema remain identical.
 Game-specific adapters only translate the raw events emitted by the connector into the universal types (session.join, combat.kill, economy.delta, milestone.complete, etc.).

Deliverable 2: Universal Game-Connector Blueprint (Framework-Agnostic)

KOBA Connector (language-agnostic template)

1. INIT
   - Detect or be told which framework is present
   - Load KOBA config (API URL, server_id, HMAC secret, region tag)
   - Register for the framework’s standard player & world events

2. IDENTITY
   - Implement GetCanonicalPlayerId(player) for this game
   - Cache mapping for the lifetime of the session

3. EVENT → CANONICAL
   - On every relevant framework event:
       extract identity + relevant payload
       map to one of the universal event types
       attach 4-part routing key [Game]-[Platform]-[Region]-[Scope]

4. SIGN & SEND
   - HMAC-SHA256(payload + timestamp + server_id)
   - Async non-blocking POST (or buffered queue)
   - Local durable buffer for offline resilience

5. BIDIRECTIONAL
   - Expose framework commands or a local HTTP endpoint
   - Map inbound KOBA actions (give item, broadcast, whitelist, kick)
     onto the framework’s native APIs

6. HEALTH
   - Periodic heartbeat with player count + connector version


The same blueprint is used whether the underlying technology is C#, Lua, Java, or C++.

Server provider must provide

[  ]  Write access to the plugins / mods / Mods folder

[  ]  Outbound HTTPS to KOBA ingest endpoints

KOBA side

[  ]  One thin connector binary/script per supported framework (or a multi-framework connector that auto-detects)
[  ]  Per-game identity mapper and event translator
[  ]  Standard onboarding test: player join → leave → one combat/economy event → confirmed receipt in KOBA

Cross-Game Telemetry & API Integration Framework for the KOBA Platform

Principal Platform Architect analysis of server data extraction archetypes, identity resolution, bidirectional control, and normalization for arbitrary multiplayer game onboarding.

───

1. Categorization of Server Data Extraction

Multiplayer games fall into four primary technical archetypes. For each, the most efficient live interception of player actions (joins/leaves, combat, economy, milestones) is listed.

A. Modded / Framework-Driven Servers
Examples: ARK: Survival Ascended (Ark Server API / ASA plugins), Rust (Oxide/uMod or Carbon + Harmony), Minecraft (Spigot/Paper plugins).

• Primary method: Native server-side plugin or Harmony hook that registers game-engine events. 
◦ ARK ASA: Ark Server API plugins hook AShooterGameMode login/logout, tames, deaths, tribe changes, inventory. Plugins such as PlayerData or ServerAnalytics persist sessions, kills, tames, and IP history to MySQL or push via HTTP.
◦ Rust: Oxide/Carbon plugins use hooks OnPlayerConnected, OnPlayerDisconnected, OnEntityDeath, Economics balance changes, raid events. Single-file plugins (e.g., TopStats) buffer and POST events; other plugins call into a shared tracker.
◦ Minecraft (Paper/Spigot): @EventHandler on PlayerJoinEvent, PlayerQuitEvent, EntityDeathEvent, economy plugins, etc. Optional REST plugins expose endpoints or fire webhooks.
• Efficiency: Event-driven (zero polling), richest data (full inventory, coordinates, damage sources), lowest latency. Requires server owner to install the KOBA connector plugin.

B. Native REST / Web Endpoint Servers
Example: Palworld.

• Primary method: Poll or long-poll the official REST API (enabled via RESTAPIEnabled=True, port 8212 by default). 
◦ Key endpoints: GET /v1/api/players (name, accountName, playerId, userId, IP, ping, location, level, building_count), GET /v1/api/metrics, GET /v1/api/info, GET /v1/api/game-data (requires -enable-gamedata-api). Write endpoints for announce/kick/ban/save.
• Efficiency: Clean structured JSON, Basic Auth. Poll every 5–15 s for joins/leaves; delta detection yields events. No combat/economy detail without deeper game-data parsing. Keep API on LAN or reverse-proxy only (official warning against public exposure).

C. Log-Tailing & Database Listeners
Examples: DayZ (.ADM admin logs + optional MySQL), Enshrouded (server logs), some older ARK setups.

• Primary method: 
◦ DayZ: Tail .ADM files (profiles folder, -adminlog). Events include connect/disconnect (with DayZ GUID / SteamID), chat, damage (hitzone, weapon, range), kills, unconsciousness, placement, build actions. Configurable via serverDZ.cfg (adminLogPlayerHitsOnly, adminLogBuildActions, etc.). Optional MySQL character_data snapshots or modern mods (LogZ) that emit NDJSON.
◦ Enshrouded: Tail enshrouded_server.log (or logs/). Lines such as [online] Session accepted with peer (id 7656119…) give SteamID64 joins; “Removed Peer” for leaves. No native RCON or rich event API yet; feature requests exist.
• Efficiency: Near-real-time with inotify/tail -F + structured parser. Lower fidelity than plugins (no guaranteed economy or inventory). Database listeners add character snapshots for progression.

D. Competitive Session Match APIs
Examples: CS2 / Valorant via Faceit, third-party match APIs, tournament webhooks.

• Primary method: External API + optional webhooks. 
◦ Faceit: Player history, stats, bans, hubs (/players/{id}/history, /players/{id}/games/{game}/stats).
◦ CS2-specific: Hosted match APIs with webhooks for match_started, match_ended, round_end, player_connected, etc.; payload includes SteamID64, kills, ADR-style metrics. Demo parsers or third-party services (csapi, GGScore, etc.) for pro/public matches.
• Efficiency: Session-level (not continuous server telemetry). Ideal for competitive leaderboards; combine with server-side logging if dedicated community servers are used.

Interception summary: Prefer framework plugins where available (richest, lowest latency). Fall back to native REST polling, then robust log parsers, then external match APIs.

4. Dynamic Data Normalization Strategy

Unified 4-part routing payload:
[Game]-[Platform]-[Region]-[LeaderboardScope]

Example: rust-steam-eu-west-weekly-pvp, palworld-steam-na-east-alltime-economy, cs2-faceit-global-season-adr.

Architecture:
1. Ingest layer (connector): Emits raw game events with original schema + extracted identity.
2. Normalizer service: 
◦ Maps game-specific metrics via per-game adapters (Rust scrap → economy.scrap, Palworld level/buildings → progression.level + progression.buildings, CS2 ADR → combat.adr).
◦ Applies unit conversion, time-window aggregation, and anti-cheat filters.
◦ Outputs canonical event types: session.join, session.leave, combat.kill, economy.delta, milestone.complete, progress.stat.
3. Router: Uses the 4-part key to shard into leaderboards, regional stores, and real-time feeds.
4. Schema (language-agnostic example):
json
{
  "koba_id": "uuid",
  "raw_ids": {"steam": "7656…", "eos": "…"},
  "game": "rust",
  "platform": "steam",
  "region": "eu-west",
  "scope": "weekly-pvp",
  "event_type": "combat.kill",
  "payload": {"victim_koba_id": "…", "weapon": "ak47", "distance": 42.5},
  "ts": "2026-10-11T19:13:00Z",
  "server_id": "cluster-01-map-a",
  "sig": "hmac-sha256…"
}


Adapters are versioned and hot-reloadable so new games can be onboarded without core changes.

Deliverable 2: Universal Game-Connector Blueprint

Language-agnostic template for a local server connector:

1. INIT
   - Load config: KOBA_API_URL, SERVER_ID, HMAC_SECRET, GAME_TYPE, AUTH_TOKENS
   - Register platform-specific listeners:
     - Plugin hooks (preferred)
     - REST poller (interval configurable)
     - Log tailer (inotify / FileSystemWatcher)
     - Optional memory/Harmony hooks

2. EVENT CAPTURE
   - On raw event → extract identity (SteamID64 / UUID / EOS / …)
   - Enrich with server context (map, region, tick)
   - Buffer in memory queue (bounded, drop oldest under pressure)

3. NORMALIZE & PACKAGE
   - Apply game adapter → canonical event
   - Attach 4-part routing key
   - Add timestamp (UTC), sequence number

4. SIGN & TRANSMIT
   - Compute HMAC-SHA256 over payload + timestamp + server_id
   - Async HTTP POST (or gRPC) to KOBA ingest endpoint
   - Retry with exponential backoff + jitter; dead-letter queue for failures
   - Optional local SQLite buffer for offline resilience

5. BIDIRECTIONAL
   - Expose local authenticated endpoint or listen for KOBA webhooks
   - Map inbound commands to RCON / native HTTP / plugin Call
   - Confirm execution and report result

6. HEALTH
   - Heartbeat every 30–60 s with player count, version, connector health
   - Graceful shutdown flushes buffer


Security: All outbound traffic TLS; secrets never logged; principle of least privilege on server file/DB access.

Deliverable 3: Onboarding Technical Requirement Checklist

Server provider / admin must allocate:

Security Tokens & Credentials
[  ]  KOBA-issued API key / HMAC secret (rotated periodically)
[  ]  Game-specific admin password (RCON, REST Basic Auth, plugin config)
[  ]  Optional Steam Web API key / Epic credentials for identity enrichment
[  ]  TLS certificates if exposing any local proxy

Firewall / Network
[  ]  Allow outbound HTTPS from game host to KOBA ingest endpoints
[  ]  Restrict RCON / REST ports to localhost or private management VLAN (never public)
[  ]  If reverse-proxy used, IP allow-list + mutual TLS preferred
[  ]  Query / game ports remain as required by the title

Server File / Process Privileges
[  ]  Read access to log directories (.ADM, logs/, ArkApi.log, etc.)
[  ]  Write access to plugin/config folders (Oxide plugins, Ark Server API plugins, Paper plugins)
[  ]  Ability to install and load the KOBA connector plugin or Harmony mod
[  ]  Read access to any required databases (DayZ MySQL character tables) with SELECT-only user
[  ]  Restart or reload capability for plugins after install
[  ]  Sufficient disk for local buffer / offline queue

Operational
[  ]  Documented server_id / cluster mapping and region tag
[  ]  Monitoring of connector process (systemd, Docker healthcheck)
[  ]  Agreement on data retention and GDPR/CCPA handling of player IDs
[  ]  Test plan: join → leave → combat/economy event → verify KOBA receipt

This framework allows any of the listed (and future) titles to be onboarded by selecting the matching archetype adapter, deploying the corresponding connector, and satisfying the checklist. Priority should be given to plugin-based extraction for depth and reliability; REST and log paths provide rapid coverage for titles that lack modding support.
